You are given:
(1) A Python method source code.
(2) Exactly ONE icontract postcondition decorator: @icontract.ensure(...).
    Optional @icontract.snapshot(...) may also be included.

Goal:
Output a JSON object that describes a Horn-rule **control-flow state machine** skeleton suitable to be compiled into Z3Py Fixedpoint (Spacer) rules.
You MUST NOT output any Z3Py code. You MUST output JSON only.

Key semantics:
- We check the postcondition ONLY over executions that return normally (no exceptions).
- If normal return requires preconditions (e.g., bounds for indexing, non-None assumptions), encode them as assumptions in early rules.
- Model control flow with relations and rules. **DO NOT compress multiple source-level branches into a few “path rules”.**
  Instead, introduce intermediate states so that rules correspond closely to source code statements / branch conditions.
- Encode a counterexample predicate Bad() by deriving it from Final with the NEGATION of the postcondition.
  IMPORTANT: Do NOT declare Bad as a relation in JSON; assume the harness already defines Bad() with no arguments.

High-level modeling requirements (IMPORTANT):
A) **Control-flow faithful (no path compression):**
   - Each rule should correspond to a small step: a statement block, a single `if`/`elif` test, a single `return`, or a single loop iteration.
   - Avoid “one rule = one full path from Init to Final”. If the code has multiple branches, create multiple intermediate relations (states).
   - In particular, for an `if / elif / else` chain, prefer:
       - One state before the chain,
       - One rule per condition to a branch state,
       - One rule from each branch state to its successor state.
B) **State naming:**
   - You may create additional relations beyond Init/Loop/Final (e.g., S0, S1, AfterSplit, CheckLen, BranchLen2, ParseVersion, ReturnTuple, ReturnNone).
   - Relation names must be unique strings and appear in "relations".
C) **Rule granularity:**
   - Each branch condition from the source should appear as its own constraint in the rule that models that branch decision.
   - Do not merge distinct branch conditions into a single large Or/And unless it directly matches a single source-level boolean test.
D) **Descriptions required:**
   - Every var must include "description" (1–2 sentences) explaining what it abstracts and where it comes from in the source.
   - Every rule must include "description" (1–2 sentences) mapping it to a source region (e.g., “models `if len(tokens) < 2: return None`”).
E) **Final semantics:**
   - Use Final(...) to represent “normal return happened” with an abstracted return value (e.g., result_is_none flag, result_version_is_int flag, etc.).
   - Do NOT put postcondition checks into Final rules. Postcondition is only used in the Bad rule as NOT(postcondition).
F) **Abstraction guidance:**
   - Use Int/Bool only unless absolutely necessary.
   - Represent complex values using Bool flags and Int summaries (e.g., tokens_len, has_version_token, version_parse_ok).
   - If needed, use additional flags to reflect outcomes (e.g., took_return_none, took_return_tuple, version_is_int).
